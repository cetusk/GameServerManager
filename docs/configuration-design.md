# 管理用設定とゲーム設定の設計方針

更新日: 2026-09-19。現行動作の基準: v0.1.0。

本書は [課題 J](backlog.md) の基本方針と、5ゲームの現行実装を整理したものです。**管理用 TOML と GUI 操作を統一し、ゲームが要求する設定形式・起動引数・初期設定手順を維持する**方針です。共通スキーマ、移行処理、初期化状態の共通 UI は今後の設計・実装対象です。

現行動作の記述は本リポジトリの実装と [サーバー設定ガイド](server-settings.md) に基づきます。各ゲームの最新公式仕様すべてを再確認した結果ではありません。対応 build ごとの実ファイル・起動結果を検証してから項目を拡張します。

## 初回生成を待つ理由

Windrose はゲーム自身が生成する設定・ワールド識別情報を読み取る必要があります。Satisfactory はそれに加えて、ゲーム内の Server Manager でサーバーの管理権設定（claim）、名前・パスワード・セッションの初期設定を行います。単に空ファイルができるまで待つ、あるいは一定秒数待つだけでは完了と判断できません。

生成を待つ対象には、ゲームが決める ID、保存形式のバージョン、複数ファイルの対応関係やセッションデータがあります。管理アプリが推測で作ると、ゲーム側の実データと食い違う可能性があります。一方、形式と反映方法を確認できた入力設定まで一律に生成禁止にする方針ではありません。

現行の Windrose は、初回起動後に停止して管理画面を再読み込みし、生成された設定を解決する手順です。新しい共通の自動待機・完了検出 UI が実装済みという意味ではありません。

## 役割の分離

| 層 | 所有する情報・役割 | 今後の方針 |
|---|---|---|
| 管理アプリの設定 | 表示設定、登録先、操作状態など | 現行の管理データを維持。すべての JSON を TOML 化する課題ではない |
| 各サーバーの管理用 `config.toml` | 設置先、SteamCMD、バックアップ先、対象の指定、起動設定など | 5ゲームで形式と共通項目を統一。ゲーム固有項目は区分する |
| ゲーム用設定・起動方法 | 公式 INI／JSON、起動引数、対応する管理 API | ゲーム固有の形式・意味・適用時期に従う |
| ゲームの保存データ | ワールド、DB、キャラクター、生成された識別情報 | ゲームが生成・更新する。管理用設定と同一視しない |

TOML を読むのは管理アプリです。ゲームが TOML を直接読む前提にはしません。ARK の旧管理用 `profile.ini` と公式の `GameUserSettings.ini`／`Game.ini` も別の用途です。

## 5ゲームの比較

| ゲーム | 現行の管理用形式 | 現行の新規作成で先に作るもの | ゲーム側で生成・初期設定するもの | 管理設定からの主な反映先 |
|---|---|---|---|---|
| ARK SA | プロファイル INI | 管理用 INI、`GameUserSettings.ini` の必要項目 | マップの保存データなど | 公式 INI と起動引数 |
| Valheim | TOML | 管理用 TOML | 指定名のワールドの保存データ | 起動引数。管理者リスト等は別ファイル |
| Conan Exiles | TOML | 管理用 TOML、`Engine.ini`、`ServerSettings.ini`、`Game.ini` の必要項目 | `game.db` などの保存データ | 公式 INI と起動引数 |
| Windrose | TOML | 初回起動用 TOML | `ServerDescription.json`、ワールド ID、保存データ・ワールド記述 | 生成後の JSON。詳細ワールド GUI は課題 K |
| Satisfactory | TOML | 初回起動用 TOML | Server Manager での初期設定、セッション、ゲームの保存データ | ポート等の起動引数。現行の管理 API 接続は主に正常停止用 |

表の「必要項目」は管理アプリが対応する範囲です。ゲームの設定全項目を初回に列挙・生成しているという意味ではありません。

### ARK SA

- **現行**: 新規作成ダイアログは `profile.ini` を提案し、管理プロファイルと `ShooterGame/Saved/Config/WindowsServer/GameUserSettings.ini` を作成します。`config.toml` がないこと自体は不具合ではありません。
- **読み書き**: 接続情報を管理プロファイルと有効な起動コマンドに反映し、RCON 関連設定などは公式 INI にも反映します。カスタム起動引数や MOD の順序を保持します。
- **今後**: 管理プロファイルを TOML に移行し、公式 INI は維持します。旧管理 INI と新管理 TOML の両方を恒久的な編集元にはしません。
- **確認事項**: 旧プロファイルの変換、相対パス、起動コマンドの上書き設定、公式 INI と引数の優先関係、移行後の正常停止。公式 `Game.ini` は必要な項目がある場合に扱い、統一のためだけに空のファイルを増やしません。

### Valheim

- **現行**: 管理 TOML からサーバー名・ポート・ワールド名・パスワード・ワールドパラメーター等の起動引数を組み立てます。新しいワールドの実データはゲームが生成します。
- **読み書き**: GUI の接続設定・ワールドパラメーター編集は管理 TOML に反映します。ワールドデータや `adminlist.txt` などは別の対象です。
- **今後**: 管理 TOML の共通部分をそろえ、既存の起動引数生成を利用します。ARK と外見を合わせるためのゲーム用 INI は新設しません。
- **確認事項**: 既存 TOML の未知項目・コメント・秘密の保持、起動引数の互換性、ワールド名と保存先の対応、複数ワールド導入時の移行。Valheim の実運用確認があっても、新スキーマへの移行は別に検証します。

### Conan Exiles

- **現行**: 管理 TOML と `ConanSandbox/Saved/Config/WindowsServer` 配下の3種類の INI を使います。新規作成では対応する設定項目を先に作成し、ワールド DB はゲーム側に任せます。
- **読み書き**: 現行コードでは、サーバー名は `Engine.ini`、参加・管理者パスワードは `ServerSettings.ini`、RCON パスワードは `Game.ini`。ポート・最大人数などは管理 TOML から起動引数へ渡します。
- **今後**: この分担を基礎に共通操作へそろえ、課題 K で詳細ワールド項目の GUI を追加します。設定変更のために `game.db` を編集・生成する設計にはしません。
- **確認事項**: INI と引数の優先関係、ゲームによる書き戻し、未知項目の保持、DB と WAL／journal の整合性。実際の build で設定が反映されることを確認します。

### Windrose

- **現行**: 初回起動用 TOML を作成し、ゲームが `ServerDescription.json` やワールド情報を生成します。生成後は停止・再読み込みして、`WorldIslandId`、対象フォルダー、`WorldDescription.json` 内の ID、保存バージョンなどを照合します。
- **読み書き**: サーバー名・パスワード等は生成済み `ServerDescription.json` に存在する一意な項目を編集します。存在しないキーや不明な構造を推測して追加しません。詳細ワールド GUI は課題 K です。
- **今後**: 初期設定が必要な状態と編集可能な状態を GUI で区別します。ゲーム生成の ID やバージョンを管理アプリが捏造せず、確認できた項目を元の JSON の位置へ書き戻します。
- **確認事項**: 対応 build のキー・ネスト構造、生成途中や複数候補の扱い、初回起動の中断・再開、ゲーム更新による保存形式の変更。現行の `Default` 保存プロファイル制約も複数ワールド設計時に検討します。

### Satisfactory

- **現行**: 初回起動用 TOML を作成します。ポート等は起動引数に渡します。サーバーの claim・名前・パスワード・初期セッションはゲーム内の Server Manager で設定します。
- **読み書き**: 管理画面の表示名は実サーバー名とは別です。API パスワード／トークン欄は、設定済み認証情報を管理アプリに教える欄であり、ゲームのパスワード変更機能ではありません。初回のコンソール停止と、認証情報登録後の HTTPS 停止を使い分けます。
- **今後**: ファイルの出現だけで初期設定完了とは判断せず、必要なユーザー操作と利用可能な管理機能を示します。将来 API で初期設定や編集を行う場合も、正式に対応する操作・認証・成功確認を別途設計します。保存ファイルを推測で合成しません。
- **確認事項**: 実際の SaveGames と管理設定の参照先、初期設定完了・認証の確認方法、専用／個人データの分離、API の対応 build。課題 L の設定保存エラーは未解決で、形式統一とは別に調査します。

## 共通の作成・登録フロー案

新規作成と既存環境の取り込みを分けたうえで、各段階の操作・結果表示をそろえます。

1. **管理対象を指定**: ゲーム、設置先、管理 TOML の保存先、バックアップ先等を入力し、対象の重複を確認する。
2. **作成内容を確認**: 管理 TOML と、先に作れるゲーム用設定の変更を提示する。既存環境では実ファイルを読み取り、初期値で上書きしない。
3. **インストール・起動**: ゲームごとの正しい実行ファイルと引数を使う。インストール完了と初期設定完了を区別する。
4. **ゲーム側の初期設定を案内**: 必要なゲームでは生成を待ち、Satisfactory では Server Manager の操作も案内する。不要なゲームに同じ待機手順を強制しない。
5. **生成結果を検証して再読み込み**: 停止・保存完了を確認して、ID・保存先・形式・認証など、そのゲームで必要な条件を満たすか確認する。
6. **通常管理へ移行**: 編集できる設定と反映時期を表示し、確認・退避・保存の共通操作で管理する。

初期化の検出を自動化する場合は、待機理由・中断・再試行を扱い、無期限の待機やファイルの存在だけによる成功判定を避けます。読み取り・検証はワーカーで行います。現行の停止中編集を維持し、稼働中スナップショット（C）とは別に設計します。

## 同じ設定の二重管理を防ぐ

- 項目ごとに正とする保存先、読み取り元、書き込み先、反映時期を定義する。ゲーム固有設定を無条件に TOML へ全複製しない。
- 起動引数と公式ファイルの両方に必要な値は、ゲームごとの優先関係を確認し、変更時に整合を検証する。管理画面の表示名とゲームの公開名など、意味の異なる値は区別する。
- 外部編集やゲーム自身による書き戻しを検出し、古い画面の内容で上書きしない。未知項目・秘密を維持し、秘密を表示・履歴へ出さない。
- 複数ファイル保存では事前検証・バックアップ・途中失敗時の回復を維持する。保存先を変える操作と、実データを移動する操作を混同しない。

## バージョン・移行・検証

- v0.1.x は現行形式での案内改善と不具合修正を段階公開する。新スキーマへの一括変換をパッチ修正に混ぜない。
- v0.2.0 候補として管理用 TOML の共通スキーマと ARK の移行を設計する。すでに TOML を使う4ゲームも、キー構造まで同一とは限らないため、互換性と変換要否を確認する。
- 旧設定を読み取り、変換内容を提示し、新形式の検証後に登録を切り替える方式を検討する。元設定を退避し、失敗時の切り戻しを用意する。具体的なスキーマ・移行 UI は未確定。
- 各ゲームで、新規作成、既存登録、外部編集、初期化の中断、未知項目の保持、移行・切り戻しを検証する。Windows 実ゲームでの起動・設定反映・正常停止を人工データの検証と分けて記録する。
