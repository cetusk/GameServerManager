# 今後の課題・棚卸し

最終更新: 2026-09-18。基準リリース: v0.1.0。

ユーザーから挙がった課題を A〜L の固定 ID で管理します。すべて未着手で、実装時期・次回リリースへの採用は未定です。以下の完了条件と着手順は検討案であり、対応済みの機能を示すものではありません。

## 管理方法

- 状態は「未着手 → 調査中 → 方針決定 → 実装中 → 検証待ち → 完了」。保留時は理由と再開条件を記録します。
- 着手時に対象ゲーム・操作・採用する完了条件を確定します。課題を分割しても元の ID との対応を残します。
- 更新時は状態、未解決事項、関連する Issue／PR／コミット、確認結果を追記します。現時点では GitHub Issue は未作成です。
- 完了時は対応リリースと検証環境を記録します。人工データのテストと Windows 実ゲームでの確認は分けます。

## 課題ごとの確認事項・完了条件案

### A — ログ履歴の削除

- 要望: ログの履歴をユーザー操作で消せるようにする。
- 確認事項: 管理ツールの作業履歴、サーバーログ、SteamCMD ログのどこまでを対象にするか。画面上の履歴消去と実ファイルの削除・切り詰めをどう扱うか。稼働中の書き込みやログ監視との整合。
- 完了条件案: 消去対象を選べて結果が画面に反映される。登録情報・未完了操作の回復記録を巻き込まず、失敗時にもログを読み続けられる。

### B — ターミナルの非表示

- 要望: 操作時にターミナルを出さない。
- 確認事項: 管理 GUI 起動用のスクリプト、ゲームサーバー、SteamCMD、停止用ヘルパーのどれが表示されるかを Windows 上で特定する。
- 完了条件案: 通常操作で不要なウィンドウが出ず、ログ取得・エラー表示・サーバーの正常停止が引き続き動く。非表示化に伴うコンソール制御の変更も確認する。

### C — ホットスナップショット

- 要望: サーバー稼働中にもスナップショットを取得する。現状の管理ツールのバックアップは停止中のみ。
- 確認事項: ゲームごとの保存要求・完了確認・整合性のある取得方法。DB、分割ワールド、キャラクターデータを含む範囲と、稼働中取得に対応できないゲームの扱い。
- 完了条件案: 対応ゲームで復元・ロードを確認できるスナップショットを作成し、失敗・未完了のコピーを成功扱いしない。復元を稼働中に許可するかは別の判断事項とする。

### D — 複数ワールドの管理

- 要望: 同一ゲームの複数ワールドを管理する。現状は各ゲームにつきサーバー1件・管理対象ワールド1つ。
- 確認事項: 1台のサーバーでワールドを切り替える運用と、複数サーバーを登録する運用の対象範囲。同時起動の要否、ポート・設置先・設定・保存先の共有可否。
- 完了条件案: ワールドを識別して登録・選択でき、操作中の切り替えで対象が変わらない。バックアップ・復元・履歴が対象ごとに分かれ、既存登録を移行できる。

### E — キャラクターデータの管理

- 要望: キャラクターデータを管理対象にする。
- 確認事項: ゲームごとにサーバー側／クライアント側のどちらがデータを持つか。管理操作を一覧表示・バックアップ・復元・移行・編集のどこまでとするか。ワールドとの対応関係。
- 完了条件案: 対象ゲームと操作を明示し、別プレイヤーや別ワールドのデータと取り違えずに処理できる。ワールドと組み合わせた復元の確認方法を定める。

### F — サーバー情報（IP:port）の表示

- 要望: 接続に使う IP アドレスとポートを管理画面で確認できるようにする。
- 確認事項: LAN 内、外部公開、待受アドレスの区別。複数 NIC、IPv6、ゲーム接続用・検索用・管理用ポートの扱い。
- 完了条件案: 接続先の用途と取得元が分かり、コピーできる。外部から接続できるか未確認の情報や、取得できない情報を明示する。

### G — playit.gg／Tailscale の接続先情報

- 要望: サービスの操作統合よりも、フォワード先のドメインまたは IP を知りたい。ユーザー記載の「talescale」は Tailscale を指す想定。
- 確認事項: 利用者へ案内する公開接続先とローカル転送先のどちらを表示するか。手動登録か既存設定からの読み取りか。playit.gg の割当先と Tailscale の IP／DNS 名の違い。
- 完了条件案: F と合わせてドメイン／IP・必要なポート・用途を表示できる。変更・未取得時の扱いを決める。トンネル作成やサービスへのログイン連携は別途要望があれば検討する。

### H — バックアップの保持上限

- 要望: 上限を設け、古いバックアップから削除する。
- 確認事項: 件数・容量・保存期間のどれで上限を設定するか。ゲーム自身のバックアップと管理ツールのスナップショットの対象区分。手動保護、設定保存前・復元前の退避データの扱い。
- 完了条件案: 新しいバックアップが正常に完成した後、設定した単位・上限に従って古い世代を削除する。作成失敗時、未完了の回復に必要な世代、他ワールドの世代を誤削除しない。

### I — ARK SA の config.toml がない件

- 報告: ARK SA で `config.toml` が見当たらない。
- 現状: ARK SA は `Profile/*.ini` 相当のプロファイル INI を登録し、ほかの4ゲームは管理用 TOML を使う。新規作成でも ARK SA はプロファイル INI と `GameUserSettings.ini` を作成する。TOML がないことだけでは生成失敗と断定できない。
- 確認事項: 新規作成・既存登録のどちらで困ったか、必要なプロファイルが生成／選択できるか、GUI の案内が実際の形式と一致しているか。
- 完了条件案: ARK SA で必要なファイルと作成／登録手順が明確になる。形式統一を採用する場合は J で移行方式を決める。
- 参照: [新規設定の作成](server-settings.md#新しいサーバーの設定を作成)、[操作ガイド](local-manager.md)。

### J — 方式統一の判断

- 要望: 幾らか変更を加えることになっても、方式を統一するか検討する。
- 未決定: 「方式」の対象。まず I に関わる管理設定形式・作成／登録手順を候補とし、保存先・管理単位・元ファイルへの反映方式まで含めるかを整理する。
- 完了条件案: 統一する部分とゲーム固有で残す部分、現状維持との比較、既存設定との互換性・移行手順を文書化し、採否を決定する。ゲーム自身が要求する INI／JSON などの形式とは区別する。

### K — Windrose／Conan のワールド設定を GUI で編集

- 要望: 元の設定ファイルにあるワールド項目を GUI 上で編集したい。
- 現状: 基本的なサーバー設定の GUI はあるが、詳細なワールド項目は元ファイル編集の案内が中心。
- 確認事項: 必要な項目と実ファイルのキー、ゲームバージョンごとの配置・型・有効範囲。Windrose の WorldDescription や Conan の設定 INI への対応範囲。
- 完了条件案: 採用項目を GUI で読み書きし、元の設定ファイルへ反映できる。未知項目・秘密・ワールドの識別情報を壊さず、外部変更と保存失敗を扱える。ゲームで反映を確認する。

### L — Satisfactory の設定保存エラー

報告された操作記録:

```text
設定の保存 を開始
設定の保存 が失敗: SaveGames に専用サーバー以外のデータがあります。専用サーバーの保存領域を分離してから登録してください
```

- 確認できた実装: `crates/games/satisfactory/src/local.rs` の `validate_saves` は SaveGames 直下で `server`、`blueprints`、`ServerSettings*.sav` 以外の名前を検出すると、このエラーを返す。
- 未確認: 実際に拒否された項目名・種類、ゲームのビルド、初回設定か既存環境か。専用サーバーの正常な生成物を誤検出したのか、個人用データが混在しているのかは未確定。
- 次の調査: 設定保存の再現手順と直下の構成を確認する。個人用データを巻き込まない保存範囲を検討し、設定保存を止める必要がある条件と、利用者が解決できる案内を整理する。
- 完了条件案: 原因を再現して対応方針を決め、正しい専用サーバー構成では保存できる。不適切な構成では理由と対応方法が分かる。検査の一律解除や、実データの削除・移動を前提にしない。
- 参照: [Satisfactory の保存先に関する制約](server-settings.md)。

## 着手順の案

1. **L・I の調査**: 現在の設定・導入で困っている点を先に切り分ける。
2. **J の方針整理**: I・L の結果を踏まえて方式変更の範囲を決める。
3. **A・B・F・G・H**: 日常操作、接続先確認、容量管理を小さな単位で改善する。G は F の表示設計と合わせる。
4. **K・D・E・C**: ゲーム固有設定と保存データの管理を段階的に広げる。D・E の管理単位と C・H の保存／保持対象を合わせて設計する。

順番は確定ではありません。独立して進められる調査や改善を、ほかの課題の完了待ちにする必要はありません。
